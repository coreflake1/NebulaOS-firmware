FINDING 1 — NO CODE REGRESSION EXISTS (PROVEN)
-------------------------------------------------
Full history of every MCU-lifecycle file
(mcu_lifecycle.py, mcu_restore.py, mcu_restart.py,
mcu_application_identify.py, mcu_known_identities.py) was walked across all
reachable commits. They have been BYTE-IDENTICAL since candidate-002's fix
(85814b6, 2026-08-28) straight through the current phase2-calibration-framework
HEAD used to build RC1. Confirmed independently the same day as RC1 by
_evidence/phase2-final-overnight-closure-20260905-012316/mcu-autoflash-investigation.txt:
`git diff 7297aeb..03a4e55 -- .../mcu_*` is empty.

There is also no dedicated "switch-to-stock" script anywhere in this
project. Switching is a manual OS-level sequence (stop klippy/moonraker,
write the OTA marker, reboot/power-cycle) that has NEVER touched
/dev/ttyS1 or the GD32 MCU at all, historically or currently — confirmed by
reading both the current sequence and the Phase 1.8B-era history.

CONCLUSION: whatever is different between "2026-08-28: hard power cycle
recovered to stock" and "2026-09-05: neither soft nor hard power cycle
recovers to stock" is NOT a source-code regression. There is nothing to
revert or restore in NebulaOS's own code.

FINDING 2 — THE 2026-08-28 "SUCCESS" WAS LIKELY AN ARTIFACT, NOT A GENERAL
MECHANISM (PLAUSIBLE, BEST-SUPPORTED EXPLANATION)
------------------------------------------------------------------------------
_project/missions/phase1.8b-candidate-002-rebuild-hardware-qualification-report.md
§4 documents EXACTLY what happened on 2026-08-28: switching to Stock never
touched the MCU by itself. The MCU only entered a bootloader-catchable
state because a PRIOR, UNRELATED manual `creality_flash.py` CLI attempt
had timed out mid-`get_version()`, leaving the chip stranded/unresponsive
at both bootloader and application level (§4.4/§4.5 of that report). Only
THEN did a hard power cycle let S13mcu_update catch a clean cold-boot
window, because the chip had no valid application to jump to and had
nothing better to do than wait for the bootloader handshake.

RC1's native candidate-001 application, by contrast, is healthy and running
(confirmed by RC1's own platform-identity table:
"MCU 'rpi': ... connected and healthy", and separately the main GD32 MCU
identifies and Klippy reaches `ready`). A healthy application's own
bootloader-handshake window on reset (soft OR hard) is plausibly too short
for S13mcu_update's cold-boot probe to catch — regardless of power-cycle
method — which would fully explain why BOTH soft and hard power cycle
failed identically on RC1, without requiring any NebulaOS code change to
explain it.

This is the same underlying explanation
_evidence/phase2-final-overnight-closure-20260905-012316/mcu-autoflash-investigation.txt
already reached independently for the soft-reboot case
("REGRESSION_EXISTS=NO"); tonight's finding extends it to also explain why
the hard-power-cycle re-test on 2026-09-05 could not reproduce the
2026-08-28 result either.

FINDING 3 — CREALITY_BOOTLOADER_PRESERVED = YES
--------------------------------------------------
See docs/mcu-flash-layout.md (written tonight) for the full source proof:
the native application's own linker layout targets the historically-known
0x08003000 post-bootloader offset (confirmed selected, not just available,
in configs/ender3-v3-ke.defconfig), and creality_flash.py's wire protocol to
the vendor bootloader has no address field at all — an out-of-range write
is structurally impossible regardless of image content or a failed/
interrupted transfer.

WHAT REMAINS UNKNOWN
-----------------------
Whether the Creality bootloader's handshake window is genuinely fixed/short
by hardware design (in which case reliable Stock recovery via a cold boot
alone was never a repeatable general mechanism to begin with, and the
2026-08-28 result was a one-off), versus something in candidate-001's own
startup path narrowing that window further than genuine Stock firmware
would (e.g. `STM32F103GD_DISABLE_SWD` auto-enabling for this target per the
same patch, ~line 277 — its effect, if any, on bootloader-handshake timing
has never been measured). Nothing in any available evidence directly times
the actual window duration under either firmware.
